# Перевірка прошивки на платі

Тут зберігаються сценарії перевірки окремих етапів міграції.
Загальний опис проєкту — у [README](../README.md).

## Етап 1: запуск і heartbeat

Мета — перевірити базовий запуск ESP-IDF, UART, конфігурацію flash та GPIO2 heartbeat.
Bluetooth і звук у цій версії ще не запускаються.
GPIO27 утримується в LOW; WS2812 може зберігати попередній колір до вимкнення живлення.

## Збірка і перевірка на платі

Відкрити цю папку у VS Code / PlatformIO. Вибрати
`Project Tasks → esp32doit-devkit-v1 → General → Build`.
Еквівалент у терміналі PlatformIO з кореня проєкту:

```powershell
pio run -e esp32doit-devkit-v1
```

Після успішної збірки користувач виконує `Upload` для потрібної ESP32,
відкриває `Monitor` на 115200 і натискає EN/RESET, щоб побачити повний запуск.
За потреби явного вибору порту (замінити COMx фактичним портом):

```powershell
pio run -e esp32doit-devkit-v1 -t upload --upload-port COMx
pio device monitor -e esp32doit-devkit-v1 --port COMx --baud 115200
```

Не запускати `erase_flash` для звичайного тесту. Якщо перевіряється плата,
на якій працювала Arduino-прошивка, Upload замінить прошивку на цій платі;
файли Arduino-проєкту залишаються незмінними.

Очікувані фрагменти логу (префікси часу, reset reason і heap можуть відрізнятися):

```text
FAITAL_SPEAKER firmware=esp-idf version=0.1.0-stage1 stage=1
ESP-IDF=6.1.0 target=esp32 ...
Reset reason: ...
Flash: configured=4194304 bytes detected=4194304 bytes
App partition: factory offset=0x10000 size=3145728 bytes
STATUS LED: GPIO=2 period=1000 ms pulse=50 ms
Stage 1 ready: application loop=10 ms; Bluetooth/audio pending
Loop alive: uptime=... s free_heap=... minimum_heap=...
```

Критерії перевірки:

1. UART читабельний; flash і app partition відповідають рядкам вище.
2. GPIO2 дає короткий спалах щосекунди.
3. 5–10 хвилин роботи: немає panic, watchdog, brownout, повторного startup banner
   або зависання; uptime зростає. Невелика початкова зміна heap допустима;
   послідовне зниження free heap потребує аналізу.
4. Після EN/RESET запуск повторюється. Окремо перевірити вимкнення/ввімкнення
   живлення без фантомного живлення через USB.
5. Надіслати стартовий лог і кілька `Loop alive`, повідомити про heartbeat.

Результат етапу 1: **PASS**, підтверджено користувачем 2026-11-08.
У наданому логу — 370 с стабільної роботи до ручного Reset і понад 2 хв після;
free heap 302304, minimum heap 302256 байт. Heartbeat працює.
Окремо підтверджений запуск після відключення живлення та USB; повторних
спотворень UART немає. Користувач зробив і опублікував коміт.

## Етап 2: A2DP, I2S і гучність із телефона

Версія застосунку — `0.2.1-stage2`, ESP-IDF 6.1.0, target ESP32.

Перший апаратний тест `0.2.0-stage2` (2026-11-08): **FAIL** — циклічний
перезапуск до `app_main`, heartbeat не запускався. ELF SHA256 починався з
`b492b08ee`; assertion — `s_prepare_reserved_regions`,
`reserved[i + 1].start > reserved[i].start`.
У ELF підтверджено накладання даних застосунку і зарезервованої пам'яті
Bluetooth з однаковим початком `0x3ffb0000`. PlatformIO повторно використав
`memory.ld` із першого етапу: його генерація не залежала від `sdkconfig.h`.

У `0.2.1-stage2` скрипт `scripts/idf_memory_layout.py` додає відсутні
залежності генерації `memory.ld` від `sdkconfig.h` та `ld.common`.
SDK і вихідні файли бібліотеки не змінюються.

Локальна перевірка виправлення 2026-11-08: `pio run -e esp32doit-devkit-v1` —
**PASS**, без попереджень компілятора. Перевірка зарезервованих ділянок зі
старого ELF відтворила помилку; у новому ELF всі 13 ділянок проходять ті самі
перевірки меж та перетинів, що й heap startup. `_data_start=0x3ffbdb60`,
`_heap_start=0x3ffcab90`; зарезервована область Bluetooth закінчується
на `0x3ffbdb5c`. ELF SHA256 починається з `506ce201a`.
Static RAM — 53292 байти, flash — 752333 з 3145728;
`firmware.bin` — 752768 байт, checksum і validation hash коректні.
Результат повторного апаратного тесту наведено нижче.

Використовується ESP32-A2DP v1.8.11 без Arduino framework, внутрішній SBC-декодер
Bluedroid і native I2S. BCK=26, WS=25, DATA=19; PCM5102A підключений як у еталоні.
Автоперепідключення та фізичні кнопки ще не перевіряємо: це наступні етапи.
Телефон може сам ініціювати вхідне з'єднання — це не автоперепідключення ESP32.

### Процедура

1. Виконати Build і Upload командами вище, відкрити Monitor на 115200.
   NVS не стирати. Стара пара з Arduino-прошивки може залишитися придатною.
2. На телефоні вибрати **Faital Bluetooth Speaker**, увімкнути медіааудіо.
   Починати прослуховування з невеликої гучності.
3. Запустити музику або знайомий тест стереоканалів. Перевірити правильність
   L/R, темп і висоту звуку, відсутність тріску та провалів.
4. Змінити гучність телефона через кілька рівнів, включно з нулем та поверненням
   до невеликої гучності. Очікуємо `Phone volume: .../127` у логу, відповідну
   зміну звуку і тишу на нулі. Якщо звук змінюється без цих логів, телефон може
   регулювати PCM сам: це ще не підтвердження AVRCP Absolute Volume.
5. Кілька разів зробити Pause/Play на телефоні. На паузі має бути тиша,
   після Play — нормальне відновлення звуку без повторення фрагмента.
6. Відтворювати 15–20 хвилин, зокрема змінюючи гучність. Heartbeat продовжується;
   немає panic, watchdog, brownout і поступового зменшення free heap.
7. Від'єднати телефон через його Bluetooth-меню та підключити знову вручну.
   Повторити після Reset і повного вимкнення живлення. Перевірити відновлення
   звуку й гучності. Пауза/від'єднання можуть залишити короткий хвіст уже
   переданого в DMA звуку (приблизно 33 мс на 44,1 кГц).
8. Якщо джерело дозволяє, перевірити окремо 44,1 і 48 кГц. Частоту підтверджує
   `SBC negotiated`, а не частота файла на телефоні. Якщо доступна лише одна,
   у результаті записати, яку саме перевірено.

### Логи й приймання

Очікувані фрагменти (значення heap, частота та гучність можуть відрізнятися):

```text
FAITAL_SPEAKER firmware=esp-idf version=0.2.1-stage2 stage=2
I2S ready: BCK=26 WS=25 DATA=19; 44100 Hz, s16 stereo Philips, APLL
A2DP ready: discoverable, waiting for phone connection
Connection: Connected
SBC negotiated: 44100 Hz, 2 channel(s); I2S s16 stereo
Audio: started
Phone volume: 32/127
PCM: rate=44100 Hz written=... dropped=0 write_errors=0
```

`written` зростає під час музики; під час стабільного відтворення
`write_errors` має залишатися нульовим, `dropped` — не зростати.
Кілька відкинутих байтів на межі паузи/від'єднання потребують зіставлення
з подіями в логу, а не автоматично означають провали під час музики.
Heap із Bluetooth буде нижчим, ніж на етапі 1; важлива його стабільність.

Надіслати лог запуску, підключення, зміни гучності, Pause/Play та статистику
після тривалого відтворення. Повідомити про якість звуку, L/R і перевірені частоти.
Коміт робить користувач після приймання тесту; до цього етап 3 не починається.

### Повторний апаратний тест 0.2.1-stage2 — 2026-11-08

**Запуск — PASS; основний функціонал підтверджено коротким тестом.
Користувач прийняв базову реалізацію, закомітив і запушив другий етап
(`4746532`) та дозволив перейти до третього.** Зауваження до переходів
між треками й скороченого часу тесту збережено нижче.

- У логу три старти з `POWERON_RESET`, кожен доходить до `app_main`,
  `I2S ready` і `A2DP ready`. ELF SHA256 — `506ce201a...`.
  Попередній assertion відсутній; panic, watchdog і brownout не зафіксовано.
  Перезапуски узгоджуються з повідомленими ручним Reset і перемиканням живлення.
- Підтверджені A2DP/SBC 44100 Hz, stereo, Pause/Play, від'єднання та повторне
  підключення телефона. Користувач також перевірив парування/розпарування,
  Reset і вимкнення/ввімкнення ESP32 та батареї.
- AVRCP Absolute Volume підтверджено логами `Phone volume`, включно з 0 і 127.
  Користувач повідомив про задовільну роботу звуку та керування гучністю.
- Усі 50 записів PCM-статистики: `dropped=0`, `write_errors=0`.
  В останньому сеансі uptime доходить до 270 с, відтворення починається
  приблизно на 8,5 с; останній PCM-запис на 261 с — 44552192 переданих байтів.
  Free heap під час відтворення — 165612..166624 байти, minimum heap — 158860,
  без послідовного зниження на цьому інтервалі.
- `Please build project in debug configuration` — повідомлення фільтра
  PlatformIO для release-збірки. `_invalid_pc_placeholder` після рядка
  `load:0x40080400` — декодування адреси завантаження тим самим фільтром,
  а не backtrace аварії.
- Одиничний `E BT_APPL: rcb[0].lidx=3, lcb.conn_msk=x1` виник до підключення
  A2DP. У коді Bluedroid це гілка відкриття AVRCP без асоційованого аудіопотоку;
  далі в цьому сеансі A2DP і гучність працюють. Є також один спотворений
  фрагмент UART близько 8,5 с; його причина з цього логу не визначена.

Невирішені питання:

- Користувач уточнив: коротке потріскування на сигналі 1000 Hz виникало
  при запуску та завершенні треку. Під час рівного відтворення потріскування
  не повідомлялося. Час цих подій у логу не позначений; точна причина
  артефактів на межах треку поки не встановлена.
  Нульові `dropped`/`write_errors` підтверджують успішні записи у драйвер I2S,
  але самі по собі не підтверджують безшумний перехід між PCM і тишею.
- Тривалість відтворення скорочено користувачем: перевірка 15–20 хвилин
  ще не підтверджена. 48 kHz у цьому логу немає.
- Для завершення перевірки виконати тривале відтворення на помірній
  фіксованій гучності. Окремо повторити початок і завершення треку та
  позначити uptime артефактів, щоб зіставити їх із подіями A2DP.

## Етап 3: перепідключення і кнопка Bluetooth

Версія — `0.3.1-stage3`, ESP-IDF 6.1.0, ESP32 DOIT DevKit V1.
Мета — перевірити останній телефон у NVS, до п'яти спроб перепідключення
та ручне парування кнопкою GPIO23. Звуковий тракт етапу 2 збережений.
Відомі короткі клацання на початку/кінці треку цим етапом не виправляються.

Локальна перевірка `0.3.0-stage3` перед апаратним тестом, 2026-11-08:
`pio run -e esp32doit-devkit-v1` — **PASS**,
без попереджень компілятора. Шість constexpr сценаріїв станів парування
пройшли перевірку під час компіляції. Це не замінює перевірку радіозв'язку.
Static RAM — 53372 байти, flash — 764369 з 3145728;
`firmware.bin` — 764800 байт. Версія, checksum/hash образу та всі 13
зарезервованих ділянок heap перевірені; накладань немає.
ELF SHA256 починається з `5a09dd8e5`.
Залежності: `espressif/button` 4.2.3, `espressif/cmake_utilities` 1.3.0;
точні версії та хеші записав Component Manager у `dependencies.lock`.

Апаратний тест `0.3.0-stage3` — **FAIL** для перепідключення після Reset.
У двох стартах перша спроба виникала до готовності A2DP і відхилялася:
`esp_a2d_source_connect:259` (`ESP_ERR_INVALID_STATE`, 0x103).
Назва цього рядка походить зі спільного коду бібліотеки; реально викликався
sink API. Адреса останнього телефона зчитувалася з NVS, ручне підключення
працювало. Після Reset у логу понад 230 с очікування без подальших спроб.

У `0.3.1-stage3` початковий запит зберігається до події успішної
ініціалізації профілю (`ESP_A2D_PROF_STATE_EVT` / `ESP_A2D_INIT_SUCCESS`).
Лише після неї запускається перша реальна спроба. Ручне парування має
пріоритет над відкладеним запитом; повторна подія готовності не створює
другу спробу. NVS, bonding і вихідні файли ESP32-A2DP не змінювалися.

Локальна перевірка `0.3.1-stage3`, 2026-11-08:
`pio run -e esp32doit-devkit-v1` — **PASS**, без попереджень компілятора.
Усі 11 constexpr сценаріїв парування й запуску пройшли перевірку під час
компіляції, включно з очікуванням готовності, повторною подією готовності
та скасуванням відкладеного запиту ручним паруванням або вхідним зв'язком.
Static RAM — 53380 байт, flash — 763953 з 3145728;
`firmware.bin` — 764384 байти. Версія та ESP-IDF у метаданих правильні,
вбудований ELF SHA256 збігається з ELF і починається з `26ebf18d0`;
esptool підтвердив checksum/hash образу. Результати подальших апаратних
перевірок записані нижче окремо від перевірки збірки.

### Поведінка

- На старті й після неочікуваної втрати зв'язку використовується reconnect
  ESP32-A2DP. Після п'яти невдалих спроб — очікування вхідного підключення.
  Тривалість спроб залежить від тайм-аутів Bluetooth; це не п'ять секунд.
- Якщо телефона ще немає в NVS, колонка одразу доступна для парування.
  Після першого успішного з'єднання перепідключення теж має працювати.
- Від'єднання з Bluetooth-меню телефона вважається навмисним: колонка
  залишається доступною, але не намагається примусово повернути цей зв'язок.
  Вимкнення Bluetooth на телефоні також може надіслати нормальне від'єднання;
  саме по собі це не тест неочікуваної втрати радіозв'язку.
- Кнопка GPIO23 активна LOW, із внутрішнім pull-up та антидребезгом 40 мс.
  Натиснути й відпустити коротко (орієнтовно 0,1–0,5 с). Довге утримання
  понад 0,8 с і повторні натискання під час активного парування не додають дій.
- При натисканні припиняються нові вихідні спроби. Поточна спроба може спершу
  завершитися або дочекатися тайм-ауту SDK; потім колонка стає доступною для
  підключення. Heartbeat і головний цикл весь цей час мають працювати.
- Парування не стирає NVS і bonding. Старий телефон може сам підключитися
  знову; для контрольованого переходу на телефон B тимчасово вимкнути
  Bluetooth на телефоні A.

### Перевірка на платі

1. Зробити звичайні Build і Upload без стирання NVS. Відкрити Monitor на
   115200, перевірити `version=0.3.1-stage3`, `stage=3`, GPIO23 і heartbeat.
2. Підключити телефон A, перевірити звук та гучність. Натиснути Reset,
   потім окремо вимкнути/увімкнути живлення без підживлення через USB.
   Колонка має сама спробувати з'єднатися з A; підтвердженням вихідної
   спроби є `Reconnect attempt`, а не лише `Connection: Connected`.
3. Вимкнути Bluetooth на A, перезапустити ESP32 і дочекатися завершення
   спроб `1/5`..`5/5` та `Reconnect limit reached`. Шостої спроби не має
   бути. Увімкнути Bluetooth і підключитися з телефона вручну.
4. Повторити старт із недоступним A, але натиснути GPIO23 під час спроби
   перепідключення. Дочекатися `Pairing: discoverable`; нові спроби мають
   припинитися. Коротко натиснути кнопку ще кілька разів — без перезапусків
   чи циклу disconnect/reconnect. Підключити телефон із його меню.
5. Під час музики з A коротко натиснути GPIO23. Дочекатися від'єднання,
   вимкнути Bluetooth на A та підключити B. Перевірити звук/гучність,
   `Manual pairing completed`, а потім Reset і холодний старт: останнім
   телефоном для перепідключення вже має бути B. Якщо другого телефона
   немає, перевірити повторне підключення A й позначити цей сценарій неповним.
6. На встановленому зв'язку перевірити неочікувану втрату сигналу
   (наприклад, вихід телефона за межі зв'язку) та повернення під час спроб.
   Після відновлення мають працювати звук і гучність. Окремо від'єднати
   телефон через його Bluetooth-меню: очікуємо спокійне очікування підключення.
7. Перевірити довге утримання GPIO23 (понад 1 с): режим не змінюється.
   Після відпускання зробити коротке натискання — воно має працювати.
   Повторити кілька циклів ручного парування/перепідключення і 15–20 хвилин
   відтворення, стежачи за heap, heartbeat, `dropped` та `write_errors`.

Перший телефон після відсутнього запису `last_bda` також має зберігатися
й перепідключатися. Цей сценарій перевіряти на платі без такого запису,
якщо вона доступна; не стирати робочий NVS лише заради тесту.

### Очікувані логи

```text
FAITAL_SPEAKER firmware=esp-idf version=0.3.1-stage3 stage=3
Starting 'Faital Bluetooth Speaker'; phone volume=0..127, fallback=64; reconnect=5 attempts
BUTTONS: Bluetooth=GPIO23 active-low pullup=internal debounce=40 ms; short release
Saved-peer reconnect deferred until A2DP is ready
A2DP ready; automatic reconnect enabled
Reconnect attempt 1/5
Automatic reconnect armed (5 attempts)
BUTTONS: Bluetooth button clicked
Manual pairing requested; automatic reconnect suspended
Pairing: waiting for disconnect
Pairing: discoverable, waiting for phone; bonds preserved
Manual pairing completed; automatic reconnect restored
```

Порядок стартових рядків може відрізнятися через паралельні задачі.
Але `A2DP ready` тепер обов'язково передує `Reconnect attempt 1/5`;
відкладений reconnect з'являється лише за наявності збереженого телефона.
`Pairing: waiting for disconnect` відсутній, якщо активного з'єднання/спроби
вже немає. Запис останнього peer сумісний з Arduino (`connected_bda/last_bda`);
його наявність не гарантує сумісності всіх bonding-даних між версіями SDK.
Якщо телефон відмовляє в автентифікації після міграції, повторити парування
через меню телефона та GPIO23; не використовувати `erase_flash` як звичайний крок.

Надіслати лог старту, невдалих спроб до ліміту, натискання під час retry,
перемикання A → B та статистику після відтворення.

### Підтверджені результати на платі — 2026-11-08

За повідомленнями користувача після виправлення `0.3.1-stage3`:

- **PASS:** після Reset телефон знову підключається автоматично.
- **PASS:** при роботі від акумулятора без USB телефон автоматично
  підключається після ввімкнення живлення.
- **PASS для початку ручного парування:** натискання кнопки від'єднує
  поточний телефон і переводить систему в режим пошуку/парування.
- **PASS за повідомленням користувача:** перевірка з ПК дала таку саму
  поведінку, як із телефоном.

Додатковий лог `0.3.1-stage3` (ELF `26ebf18d0`) і повідомлення користувача
підтвердили два сценарії:

- **PASS:** спроби `1/5`..`5/5` завершуються `Reconnect limit reached`
  на 7,894 с; до кінця цього запуску на 42 с шостої спроби немає.
  Heap під час очікування стабільний — 173924 байти.
- **PASS:** кнопка під час третьої спроби на 13,274 с вимикає reconnect;
  на 14,274 с колонка стає discoverable. Наступних вихідних спроб немає.
  Ручне підключення завершується `Manual pairing completed` і `Connected`
  на 25,374 с, автоматичне перепідключення знову дозволене.

У логу також підтверджено правильний порядок `A2DP ready` перед першою
спробою та успішне стартове підключення. У фрагменті відтворення 44,1 kHz
`dropped=0`, `write_errors=0`; паніки чи watchdog reset не зафіксовано.
При скасуванні під час відкриття з'єднання SDK спочатку повідомляє
`unhandled event:BTC_AV_DISCONNECT_REQ_EVT`, після чого адаптер завершує
від'єднання. Є також діагностичні рядки BT_APPL/BT_OSI, зокрема
`alarm_set failed to start timer, err 0x103`, і один пошкоджений фрагмент
UART. У цьому тесті вони не завадили завершити сценарії; їхні причини
окремо не перевірені.

Окремо не підтверджені повторні натискання/довге утримання, втрата
радіозв'язку, кероване від'єднання через меню, збереження нового останнього
пристрою після перемикання A → B із наступним Reset і 15–20 хвилин
відтворення зі статистикою.

**Основні перевірені сценарії етапу 3 — PASS; повна регресія ще не завершена.**
Користувач підтвердив роботу і запросив текст коміту; коміт робить користувач.
